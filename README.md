# shortly — Flutter + Go

Единый проект: Flutter-клиент в корне, Go-сервис в backend/.
Создание короткой ссылки, копирование, QR-код с сервера, удаление с подтверждением,
локальная история между запусками. Интерфейс на русском, адаптируется к ширине экрана.

## Запуск

Все команды выполняются из корня этого репозитория. Нужны Flutter и Docker Desktop.
Запустите Docker Desktop, затем:
```sh
docker compose up -d --build
docker compose logs -f backend
```

В другом терминале, из той же папки:
```sh
flutter pub get
flutter run -d chrome --dart-define=API_BASE_URL=http://localhost:8080
```

Android Emulator:
```sh
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8080
```

На физическом устройстве используйте доступный адрес сервера в вашей сети.
API_BASE_URL — адрес origin без пути, параметров и фрагмента.
По умолчанию: http://localhost:8080. Для release используйте HTTPS:
```sh
flutter build web --dart-define=API_BASE_URL=https://api.example.com
```

Android имеет INTERNET permission; незашифрованный HTTP разрешён только в debug.
Для iOS используйте HTTPS; исключения ATS для произвольного HTTP не добавлялись.
HTTPS-страница браузера также должна обращаться к HTTPS API.
CORS_ALLOWED_ORIGIN на сервере должен разрешать origin Flutter Web.

Адрес коротких ссылок формирует бэкенд из URL_BASE в .env (или url.base в backend/configs/config_local.yaml).
При работе с телефоном localhost в этой настройке нужно заменить на доступный
телефону адрес. API_BASE_URL не переписывает полученные короткие ссылки:
это сохранило бы несоответствие с QR-кодами, которые генерирует сервер.


## Что лежит в репозитории

- lib/, test/, android/, ios/, web/ — Flutter-приложение и его платформы.
- backend/cmd/, backend/internal/ — исходники Go.
- backend/go.mod, backend/go.sum — зависимости сервера.
- backend/migrations/ — SQL для новой базы.
- backend/configs/ — конфигурация локальной разработки.
- backend/web/ — исходная статическая страница сервера, сохранённая для маршрута /.
- docker-compose.yml — Go, PostgreSQL, Kafka и ZooKeeper.

Отдельный старый frontend-контейнер не нужен: основное приложение теперь Flutter.
Файлы из исходного проекта скопированы, исходная папка не удалена.
Вложенный .git и скомпилированный backend/main не переносились.

### Если старый бэкенд уже запущен

Два набора контейнеров используют одинаковые порты. Перед запуском новой копии
остановите старые контейнеры командой docker compose stop из старой папки.
Новый Compose создаёт отдельный том PostgreSQL: существующие ссылки и данные
из старой базы автоматически не переносятся. Старый том не удаляйте.
Для работы с прежней базой можно продолжать использовать старый запущенный
бэкенд — API клиента остаётся тем же.

### Настройки

При необходимости скопируйте .env.example в .env и задайте URL_BASE
(обязательно с завершающим /) и CORS_ALLOWED_ORIGIN.
Пароль postgres в локальном YAML и Compose — демонстрационная настройка,
предназначенная только для разработки. Настоящие секреты не коммитьте.

## Архитектура

FSD: app → pages → features → entities → shared.
Слои импортируют нижележащие, без обратных зависимостей.
В слайсах выделены сегменты model, api и ui; внешние импорты идут через
публичные экспорты short_link.dart, manage_links.dart и shortener.dart.
Пустой слой widgets не создавался: переиспользуемых составных блоков пока нет.

- app: приложение, тема.
- pages/shortener: сборка экрана и диалогов.
- features/manage_links: сценарии создания/удаления, валидация и Riverpod-состояние.
- entities/short_link: сущность, интерфейсы репозитория и истории, их реализации.
- shared/api: HTTP, таймаут, преобразование транспортных ошибок.
- shared/config: проверка адреса API.
- main.dart: composition root — связывает реализации с интерфейсами через ProviderScope.

Поток: действие пользователя → LinkController → LinkRepository → ApiClient → Go.
После успешного ответа контроллер обновляет список и сохраняет его через LinkHistory.
Виджеты подписываются на состояние; сетевых запросов непосредственно в build нет.
QR загружается отдельно и не вызывает редирект, поэтому просмотр QR не увеличивает клики.

SOLID: транспорт, хранение, сценарии и UI имеют отдельные ответственности.
Контроллер зависит от узких интерфейсов LinkRepository/LinkHistory.
Для тестов HTTP и хранилище заменяются без изменения контроллера.
Riverpod оставлен из исходного проекта; дополнительный BLoC и генерация кода
для этого объёма не нужны. HTTP-клиент закрывается при уничтожении провайдера.

История разделена по origin API и хранится в SharedPreferencesAsync.
Это удобство пользователя, а не резервная копия: очистка данных приложения её удалит.
Не храните здесь конфиденциальные URL. На сервере нет пользовательского списка ссылок.
При сбое записи результат остаётся на экране с предупреждением.
POST автоматически не повторяется: после сетевого таймаута сервер мог уже создать ссылку.
Удаление 404 считается успешным: нужного ресурса уже нет.

## Контракт и ограничения сервера

- POST /api/v1/shorten, JSON {"url":"https://example.com"} →
  short_url, expires_at (Unix seconds, 0 = бессрочно), click_count.
- DELETE /:code → 204.
- GET /:code/qr → PNG.
- GET /:code → редирект; клиент его не использует для проверки существования.
- Авторизации, списка и API актуальной статистики нет. Счётчик кликов в UI не
  показывается, поскольку ответ создания не даёт актуального значения в дальнейшем.
- В backend/internal/service/url_normalizer.go весь URL переводится в нижний
  регистр. Это может ломать регистрозависимые пути и query-параметры.
  Клиент сохраняет и передаёт регистр; исправление требуется на стороне Go.
- DELETE доступен без авторизации. Перед публичным коммерческим запуском нужна
  серверная проверка прав: скрытие кнопки на клиенте не защищает API.

Логика Go-сервиса сохранена; Dockerfile адаптирован к общей структуре.

## Проверки

```sh
flutter analyze
flutter test
flutter build web
```

Тесты проверяют контракт HTTP, ошибки ответа, идемпотентное удаление 404,
валидацию формы, создание и подтверждённое удаление, сохранение результата
при ошибке локальной записи и сохранение ссылки при ошибке удаления.
Интеграцию с запущенными PostgreSQL/Kafka/Go нужно проверять отдельно.

Для самостоятельного разбора проследите create() от кнопки до HTTP и обратно.
Безопасное упражнение: добавить фильтр истории по исходному адресу, не меняя API.
